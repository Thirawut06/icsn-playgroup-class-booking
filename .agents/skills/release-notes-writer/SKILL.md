# Release Notes Writer

## Overview
Skill นี้ทำหน้าที่เขียน release notes ภาษาไทยที่กระชับ อ่านง่าย และเน้นไปที่ **ผลลัพธ์ที่ผู้ใช้จะได้รับ (Outcomes)** ในรูปแบบคล้ายบริษัทระดับโลก (เช่น Linear, Notion) โดยบังคับดึงข้อมูลเปรียบเทียบจาก `origin/main` เสมอ เพื่อหลีกเลี่ยงข้อผิดพลาดจากการดึงประวัติเก่าใน Local มาเขียนซ้ำ

## Workflow

### Step 1: รวบรวมข้อมูลดิบอย่างแม่นยำ
รันคำสั่งเหล่านี้เพื่อดูความเปลี่ยนแปลงที่แท้จริงจาก Production (เทียบกับ `origin/main` เสมอ):
```bash
git fetch origin main
git log origin/main..HEAD --oneline --no-merges
git diff origin/main..HEAD --name-status
```
*⚠️ ห้ามใช้ `git log main..HEAD` ธรรมดาเด็ดขาด เพื่อป้องกันปัญหาดึงของเก่ามาเขียนซ้ำ*

### Step 2: วิเคราะห์และแปลภาษาเทคนิคเป็น "คุณค่าต่อผู้ใช้"
- **Focus on Outcomes:** แปลง Commit ทางเทคนิคเป็นประโยชน์ที่ผู้ใช้หรือแอดมินได้รับ 
  - *ห้ามเขียน:* "ลบแพ็กเกจ X" หรือ "Refactor Component Y"
  - *ให้เขียน:* "ระบบโหลดไวขึ้น" หรือ "แอปทำงานลื่นไหลและเสถียรขึ้น"
- **Customer-Centric & Specific:** ระบุให้ชัดเจนว่าเปลี่ยนอะไร ตรงไหน แต่อย่าใช้ศัพท์เทคนิค
- **Scannable:** ประโยคต้องกระชับ สั้น อ่านผ่านๆ (Scan) แล้วรู้เรื่องทันที ไม่เวิ่นเว้อ

### Step 3: จัดหมวดหมู่ (Scannable Structure)
แบ่งสิ่งที่เปลี่ยนเป็น 4 หมวดหลัก:
1. ✨ **มีอะไรใหม่และปรับปรุง (Improvements)** - ฟีเจอร์ใหม่หรือของเดิมที่ดีขึ้น 
   - แบ่งย่อยหมวดนี้เป็น: **ประสบการณ์ของผู้ปกครอง (Parent Experience)** และ **การจัดการของแอดมิน (Admin Experience)**
2. 🐛 **แก้บั๊ก (Bug Fixes)** - ปัญหาที่ถูกแก้ไขให้กลับมาทำงานตามปกติ
3. 🛠 **ระบบภายใน (Under the Hood)** - การปรับปรุงโครงสร้าง โค้ด ความปลอดภัย (รวมเรื่องเทคนิคไว้ที่นี่ แต่อธิบายด้วยภาษาง่ายๆ)
4. ⚠️ **ต้องระวัง (Breaking Changes)** - (ใส่เฉพาะตอนที่มี) การเปลี่ยนแปลงที่ทำให้พฤติกรรมแอปเปลี่ยนไป ผู้ใช้ต้องปรับตัว

### Step 4: เขียน release notes (ข้อความล้วน)
**Template:**
```markdown
# บันทึกการอัปเดต v{VERSION}

📅 {วัน เดือนภาษาไทย ปีพุทธศักราช}

---

✨ **มีอะไรใหม่และปรับปรุง (Improvements)**

**ประสบการณ์ของผู้ปกครอง (Parent Experience)**
- **[ชื่อฟีเจอร์สั้นๆ]:** [อธิบายผลลัพธ์ว่าผู้ใช้ได้อะไร]

**การจัดการของแอดมิน (Admin Experience)**
- **[ชื่อฟีเจอร์สั้นๆ]:** [อธิบายผลลัพธ์ว่าแอดมินทำงานง่ายขึ้นยังไง]

---

🐛 **แก้บั๊ก (Bug Fixes)**
- **[ชื่อส่วนที่พัง]:** [อธิบายปัญหาเดิมและวิธีแก้ชัดเจน]

---

🛠 **ระบบภายใน (Under the Hood)**
- **[หัวข้อ]:** [สิ่งที่เปลี่ยนแปลงระดับโครงสร้างและผลลัพธ์ตามจริง]
```
*(ถ้าไม่มีเรื่องให้เขียนในหมวดไหน ให้ตัดหมวดนั้นทิ้งไปเลย ไม่ต้องใส่ค้างไว้)*

### Step 5: กำหนดเลขเวอร์ชันและบันทึกไฟล์
ใช้ **Semantic Versioning (MAJOR.MINOR.PATCH)**
- **MAJOR:** ขยับเลขแรก (เช่น 1.0.0 -> 2.0.0) หากมีหมวด `⚠️ ต้องระวัง` หรือเป็นฟีเจอร์ใหญ่ระดับพลิกโฉม
- **MINOR:** ขยับเลขกลาง (เช่น 1.0.0 -> 1.1.0) หากมีเนื้อหาในหมวด `✨ มีอะไรใหม่และปรับปรุง`
- **PATCH:** ขยับเลขท้าย (เช่น 1.0.0 -> 1.0.1) หากมีแค่หมวด `🐛 แก้บั๊ก` หรือ `🛠 ระบบภายใน`

บันทึกเป็นไฟล์ `releases/v{VERSION}.md` (เช่น `releases/v1.1.0.md`)

### Step 6: สรุปผลให้ผู้ใช้ทราบ
เมื่อเขียนเสร็จ ให้บอกชื่อไฟล์ และแสดงตัวอย่างสั้นๆ ให้ผู้ใช้อ่าน พร้อมแนะนำให้ทดลองกด Stage ไฟล์เพื่อเตรียม Commit
