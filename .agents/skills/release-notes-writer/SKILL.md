# Release Notes Writer

## Overview

Skill นี้ทำหน้าที่เขียน release notes ภาษาไทย กระชับ อ่านง่าย สำหรับทีมงานที่ไม่ใช่ developer
โดยเปรียบเทียบสิ่งที่เปลี่ยนแปลงระหว่าง git tag ก่อนหน้ากับ HEAD ปัจจุบันบน main (= production)

## Workflow

### Step 1: รวบรวมข้อมูลดิบ

**1. เช็กความต้องการของผู้ใช้ (Timeframe Filtering):**
หากผู้ใช้สั่งว่า "สรุปของวันนี้" ให้ดึงเฉพาะ Commit ของวันนี้โดยไม่ต้องอิงตาม Tag เก่า เพื่อป้องกันการนำฟีเจอร์เก่าที่ยังไม่ได้ release มารวมด้วย:
```bash
# ใช้สำหรับกรณี "ของวันนี้" หรือ "ล่าสุดจริงๆ"
git log --since="midnight" --oneline --no-merges
git diff HEAD@{midnight}..HEAD --name-only
```

**2. รันคำสั่งปกติ (หากผู้ใช้ไม่ได้ระบุเวลา):**
หากผู้ใช้สั่งเขียน Release Notes ปกติ ให้เปรียบเทียบกับ Tag ล่าสุดตามมาตรฐาน:
```bash
# ใช้ Powershell Syntax สำหรับ Windows
$tag = git describe --tags --abbrev=0
git log $tag..HEAD --oneline --no-merges
git diff $tag..HEAD --name-only
node -p "require('./package.json').version"
```

นอกจาก commit messages ให้ inspect ไฟล์ที่เปลี่ยนด้วย:

| Path | บอกอะไร |
|---|---|
| `src/components/book/` | ฟีเจอร์ฝั่งผู้ปกครอง |
| `src/components/admin/` | ฟีเจอร์ฝั่งแอดมิน |
| `src/app/[lang]/` | หน้าใหม่ / routing |
| `supabase/migrations/*.sql` | ฐานข้อมูลเปลี่ยนแปลง |
| `supabase/functions/` | ระบบ automation ใหม่ |
| `src/lib/services/` | business logic ใหม่ |

### Step 2: จัดหมวดหมู่

แบ่งสิ่งที่เปลี่ยนเป็น 4 หมวด:

| หมวด | รวมอะไร |
|---|---|
| ✅ เพิ่มใหม่ | ฟีเจอร์ใหม่ หน้าใหม่ ระบบใหม่ |
| 🔧 ปรับปรุง | ของเก่าที่ทำงานดีขึ้น เร็วขึ้น ใช้ง่ายขึ้น |
| 🐛 แก้บั๊ก | ของเก่าที่พัง/ผิดพลาด และได้รับการแก้ไข |
| ⚠️ ต้องระวัง | สิ่งที่เปลี่ยนแล้วอาจกระทบการใช้งาน เช่น หน้าย้ายที่ ปุ่มหาย ต้องทำอะไรใหม่ |
| 🛠 ระบบภายใน | การอัปเดตโครงสร้างระบบ (เช่น อัปเดตแพ็กเกจ, CI/CD, ความปลอดภัย) ที่ทีมควรทราบแม้ผู้ใช้ทั่วไปจะมองไม่เห็น |

**ข้อควรระวัง:** ซ่อนเฉพาะ commit ที่เป็นเรื่องทางเทคนิคล้วนๆ (เช่น การจัดหน้าโค้ด `style:`) แต่หากเป็นการปรับปรุงระบบหลังบ้านที่มีผลกับความเสถียร (เช่น `chore: setup ci/cd`) ให้นำมาสรุปในหมวด "ระบบภายใน" ด้วยความจริงตามตรง

### Step 3: แบ่งย่อยตาม Audience

ในแต่ละหมวด ถ้ามีเนื้อหาของทั้งสองกลุ่ม ให้แบ่งย่อย:

```
✅ เพิ่มใหม่

**ฝั่งผู้ปกครอง**
- ...

**ฝั่งแอดมิน**
- ...
```

ถ้าหมวดนั้นมีเฉพาะฝั่งเดียว ไม่ต้องแบ่งย่อย เขียน bullet ตรงๆ ได้เลย

### Step 4: เขียน release notes

**กฎการเขียน:**
- ใช้ภาษาไทยที่เข้าใจง่าย แต่ **ต้องตรงไปตรงมา ชัดเจน อิงตามความเป็นจริง และไม่อ้อมค้อมหรือใช้คำสวยหรูจนกำกวม**
- หลีกเลี่ยงศัพท์ Tech ที่ซับซ้อน แต่ **ต้องอธิบายรายละเอียดให้ครอบคลุมและครบถ้วนพอที่ทีมงานจะเข้าใจว่าเกิดอะไรขึ้นจริงๆ** (เช่น ถ้าเพิ่มระบบบอทแจ้งเตือน ให้อธิบายชัดเจนว่าบอททำหน้าที่แค่แจ้งเตือน ไม่ใช่อัปเดตระบบให้เอง)
- เน้นที่ความจริงว่า **ผู้ใช้หรือทีมงานได้ประโยชน์อะไร หรือต้องเตรียมตัวรับมือกับอะไร** ห้ามเขียนอวดอ้างเกินจริง
- อนุญาตให้เขียน 1-2 ประโยคต่อ bullet ได้ หากจำเป็นต้องให้รายละเอียดที่ครบถ้วน
- ถ้าไม่มีเนื้อหาในหมวดนั้น ให้ตัดหมวดนั้นออกทั้งหมด ไม่ต้องใส่ว่าว่าง

**Template:**

```markdown
# บันทึกการอัปเดต v{VERSION}

📅 {วัน เดือนภาษาไทย ปีพุทธศักราช}

---

✅ เพิ่มใหม่

**ฝั่งผู้ปกครอง**
- {สิ่งที่เพิ่มใหม่}

**ฝั่งแอดมิน**
- {สิ่งที่เพิ่มใหม่}

---

🔧 ปรับปรุง
- {สิ่งที่ดีขึ้น}

---

🐛 แก้บั๊ก
- {สิ่งที่แก้ไข อธิบายปัญหาเดิมและวิธีแก้ชัดเจน}

---

🛠 ระบบภายใน
- {สิ่งที่เปลี่ยนแปลงในระดับโครงสร้าง พร้อมอธิบายผลลัพธ์ตามความเป็นจริง}

⚠️ ต้องระวัง
- {สิ่งที่เปลี่ยนแล้วอาจกระทบ}
```

**รูปแบบวันที่ไทย:** ใช้พุทธศักราช (+543) เช่น `13 กรกฎาคม 2569`

เดือนภาษาไทย:
มกราคม, กุมภาพันธ์, มีนาคม, เมษายน, พฤษภาคม, มิถุนายน,
กรกฎาคม, สิงหาคม, กันยายน, ตุลาคม, พฤศจิกายน, ธันวาคม

### Step 5: กำหนดเลขเวอร์ชันและบันทึกไฟล์

ให้วิเคราะห์การเปลี่ยนแปลงทั้งหมดแล้วกำหนดเลขเวอร์ชันถัดไปตามหลัก **Semantic Versioning (SemVer)** (MAJOR.MINOR.PATCH):
- **MAJOR:** ขยับเลขแรก (เช่น 1.0.0 -> 2.0.0) ถ้ามีเนื้อหาในหมวด `⚠️ ต้องระวัง` (มีการแก้ไขที่เปลี่ยนพฤติกรรมระบบเดิมชัดเจน ผู้ใช้ต้องปรับตัว)
- **MINOR:** ขยับเลขกลาง (เช่น 1.0.0 -> 1.1.0) ถ้ามีเนื้อหาในหมวด `✅ เพิ่มใหม่` (มีฟีเจอร์ใหม่)
- **PATCH:** ขยับเลขท้าย (เช่น 1.0.0 -> 1.0.1) ถ้ามีแค่หมวด `🔧 ปรับปรุง` หรือ `🐛 แก้บั๊ก` (ไม่มีฟีเจอร์ใหม่)

เช็กเวอร์ชันล่าสุดที่ปล่อยไปจากชื่อไฟล์ในโฟลเดอร์ `releases/` หรือจาก Git Tag ล่าสุด เพื่อนำมาคำนวณเวอร์ชันถัดไป

บันทึกออกมาเป็น:
```
releases/v{VERSION}.md
```

เช่น `releases/v1.0.1.md`, `releases/v1.1.0.md`

### Step 6: แจ้งให้ผู้ใช้รู้

หลังเขียนเสร็จ แสดง:
1. ชื่อไฟล์ที่สร้าง
2. Preview ของ release notes ที่เขียน
3. แนะนำให้รัน `npm run release` เป็นขั้นตอนถัดไป

## สิ่งที่ไม่ทำ

- ❌ ไม่เขียนลงใน `CHANGELOG.md` (นั่นเป็นหน้าที่ของ `release-it`)
- ❌ ไม่รวมกับ `RELEASE_NOTES.md` เดิม (เก็บแยกต่อ version)
- ❌ ไม่เขียนภาษาอังกฤษหรือศัพท์ tech ที่ทีมงานไม่เข้าใจ
- ❌ ไม่ commit หรือ push โดยไม่ได้รับอนุญาตจากผู้ใช้
